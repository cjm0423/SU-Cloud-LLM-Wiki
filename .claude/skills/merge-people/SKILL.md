# /merge-people — 여러 참여자 자료 통합

여러 사람이 **같은 주제를 각자 학습·기록한** inbox 원본을 하나의 위키로
통합한다. 참여자가 2명이든 3명이든 N명이든 절차는 동일하다. 참여자들이
대체로 같은 범위를 다루므로, 핵심은 "누구 문서를 채택하느냐"가 아니라
**한 문서 안에 여러 관점을 융합하고 출처를 남기는 것**이다.

관련 배경·진행 상태가 메모리에 있으면(예: 특정 통합 프로젝트) 작업 시작 전
참고한다.

## 0. 참여자와 원본 파악

먼저 이번에 통합할 **참여자 목록**을 확정한다. 사람이 명시하지 않았으면
`00_Inbox` 구조에서 추론하되, 애매하면 AskUserQuestion으로 물어본다.

inbox의 참여자별 배치는 두 가지 형태가 섞일 수 있다:

- **flat**: `00_Inbox/<주제>-raw.md` (서브폴더 없이 루트에 둔 사람)
- **서브폴더**: `00_Inbox/<이름>/...` (사람별 폴더로 둔 사람)

`00_Inbox`를 Glob으로 훑어 각 참여자의 원본을 찾고, **같은 주제를 다루는
원본끼리 묶어 세트**를 만든다. 한 세트가 곧 통합 문서 하나의 소스다.

## 1. 문서 유형별 통합 기준 (확정)

| 문서 유형 | 통합 방식 |
|---|---|
| 개념 (`01_Concepts`) | **통합** — 1개념 1문서. 참여자 전원 내용을 한 문서에 융합, `raw_source`에 모든 원본 기록 |
| 가이드 (`03_Guides`) | **절차별 분리** — 같은 절차면 통합, 다른 환경/장비면 분리(≈사람별) |
| 트러블슈팅 (`02_QnA`) | **사건별 1문서** — 한 사건당 한 문서, 담당자 표기 |
| 회의(`04`)·결정(`06`) | **공동 1문서** — 사람별로 나누지 않음 |
| 주차 학습기록 | **inbox raw로 보존** — 위키 문서화하지 않음 |

판단이 애매하면(예: 같은 절차인가 다른 환경인가) 추측하지 말고
AskUserQuestion으로 사람에게 물어본다.

## 2. 융합 원칙 — 원본을 전문으로 읽어라 (⚠️ 최우선 교훈)

**절대 헤딩만 보고 요약하지 않는다.** 과거 전면 재작성에서 원본을 헤딩만
보고 압축해 분량이 절반으로 줄어든 사고가 있었다(HA 219→78줄,
Kolla-Install 423→107줄). 반드시:

- 참여자 전원의 원본을 **본문 전체까지 Read**하고 쓴다.
- 여러 사람이 겹치는 내용은 한 번만, **한 사람만 가진 고유 디테일은 반드시
  살린다.** 융합의 가치는 이 고유 디테일에 있다.
- 실측 수치·패킷 트레이스·flow table·명령어 출력 등 구체 근거는 요약하지
  말고 원문 그대로 옮긴다.
- 참여자들의 설명이 **상충**하면 임의로 한쪽을 고르지 말고, 양쪽을
  병기하거나 "확인 필요"로 표시하고 사람에게 알린다.

## 3. 출처(provenance) 기록

통합 문서의 frontmatter `raw_source`에 채택한 원본을 **배열로** 남긴다.
참여자 수만큼 항목이 들어간다:

```yaml
raw_source:
  - "[[00_Inbox/openstack-overview-raw]]"
  - "[[00_Inbox/민기/W03-openstack]]"
  - "[[00_Inbox/원지/W03-네트워크]]"
```

특정 주제를 한 사람만 다뤘으면 그 한 명만 기록한다 — 억지로 참여자 전원을
채우지 않는다.

## 4. 고유 대형 기여는 별도 문서로

한 사람만 깊게 판 주제는 개념에 억지로 섞지 말고 dedicated 문서로 둔다.
inbox를 훑을 때 어느 참여자에게만 있는 대형 주제(실측 매트릭스, 특정 장비
셋업, 특정 사건 트러블슈팅 등)를 식별해 별도 문서 후보로 표시한다. 새
dedicated 문서가 필요하면 `promote-inbox` 기준(템플릿·태그·INDEX)을 따른다.

## 5. 계보(위임) 문서는 중복 주입하지 않는다

일부 문서는 세부를 다른 문서에 **의도적으로 위임**하는 계보 문서다
(예: 상위 개요 문서가 컴포넌트 상세를 전용 아키텍처 문서로 위임). 이런
문서엔 위임 대상에 이미 있는 내용을 중복으로 주입하지 않는다. 기존 문서를
고칠 때 그 문서가 위임 구조인지 먼저 확인한다.

## 6. 태그·메타데이터

- `tags`는 `TAXONOMY.md`의 통제 어휘에서만. 작성 전 `TAXONOMY.md`를
  읽는다. 문서당 2~5개, `type` 중복 태그 금지, 환경 축 하나는 붙인다.
- 새로 만든 통합 문서의 `status`는 기본 `draft`. `stable` 승격은
  `review-status` 스킬의 몫 — 여기서 올리지 않는다.
- 통합에 참여한 사람이 `05_People/`에 없으면 스텁 생성(`promote-inbox` 4단계
  절차와 동일). 여기서 참여자 목록이 그대로 쓰인다.

## 7. 원본 상태 갱신

통합에 사용한 `00_Inbox` 원본들의 frontmatter를 `status: "promoted"`,
`promoted_to: "[[대상폴더/문서명]]"`로 바꾼다. 한 통합 문서에 쓰인 여러
참여자 원본을 **전부** 갱신한다. **원본 본문은 절대 수정·삭제하지 않는다**
— 검증용이므로 그대로 보존, frontmatter만 바꾼다. 주차 학습기록처럼
위키화하지 않기로 한 원본은 `raw`로 둔다.

## 8. INDEX.md 갱신 & 커밋

- 목적지 폴더 `INDEX.md` 수동 목록에 새 문서 줄 추가(Dataview 블록은 건드리지
  않음).
- **문서(주제) 단위로 커밋을 나눈다.** 여러 개념을 한 커밋에 뭉치지 않는다.
- 커밋 메시지 형식: `feat: <주제> 통합` 또는 깊은 재융합이면
  `feat: <주제> 깊은 재통합 — <핵심 추가내용>`.
- **push는 하지 않는다.** 사람이 확인 후 명시적으로 요청했을 때만.

## 9. 마무리

- `wiki-lint`로 깨진 링크·INDEX 불일치·status 오류를 점검한다.
- 진행 상태를 관련 메모리에 갱신한다(어떤 문서를 누구의 자료로 어느 깊이로
  통합했는지, 남은 것, push 여부).

## 하지 말 것

- **헤딩만 보고 원본을 요약하지 않는다** — 반드시 본문 전문을 읽는다(2절).
- `00_Inbox` 원본 본문을 덮어쓰지 않는다(frontmatter만).
- 이미 `status: promoted`인 원본을 다시 처리하지 않는다.
- 한 사람만 가진 고유 디테일을 "중복인 줄 알고" 버리지 않는다.
- 참여자들이 상충할 때 임의로 한쪽을 채택하지 않는다 — 병기하거나 물어본다.
- 계보 문서에 위임 대상의 내용을 중복 주입하지 않는다(5절).
- `TAXONOMY.md`에 없는 태그를 새로 만들지 않는다.
- 여러 주제를 한 커밋에 묶지 않는다. push하지 않는다.
